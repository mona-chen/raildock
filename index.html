How it works

Four concepts. Everything else follows.

RailDock organizes your infrastructure into a hierarchy that maps to how you actually think about deployments.

🖥
Servers
Add any Linux server by SSH key and hostname. RailDock validates the connection, detects the runtime version and active proxy type, and stores your SSH key encrypted at rest (AES-256-GCM). The install script auto-wires your local server so you can deploy in under five minutes — and can provision brand-new remote hosts end-to-end.
📁
Projects
A project is a logical grouping of services that belong together — typically one application plus its databases and workers. Every project gets a private Docker bridge network (named rd-{slug}-{id}) so services can reach each other by internal hostname without going through the public internet.
⬡
Services
A service is anything you deploy: a web app, a background worker, a Postgres database, Redis, MySQL, MongoDB, or any Docker image. Apps can be built from a git repository (Nixpacks, Dockerfile, Railpack, Herokuish, Cloud Native Buildpacks, or Lambda) or deployed directly from a Docker image tag.
🔗
Links
Linking an app to a database wires them together on the project network and injects the connection string (like DATABASE_URL) into the app's environment automatically. RailDock reads the injected connection details back and mirrors them into the service record so you can see them in the UI — no manual configuration.

Capabilities

Built for what running software actually requires

Not a feature checklist. These are the things RailDock does that save you from writing shell scripts at 2am.

Real-time log streaming
Logs stream over an ActionCable WebSocket using a dedicated SSH connection. The frontend strips ANSI codes, detects log levels (fatal/error/warn/info/debug/trace) from message content, and pretty-prints JSON payloads. For databases, the correct runtime log command is used automatically.
streaming over SSH
Interactive terminal
A full PTY session into any running container via xterm.js. Forwards keystrokes and resize events directly to the SSH channel. Supports shell selection (sh, bash, zsh, ash) and is restricted to project owners and org admins — not all users.
PTY over WebSocket
Secret injection with stable IDs
Use ${{ secret() }} in your manifest or template. RailDock generates a random value on first deploy and keeps it stable on subsequent deploys — you never see the raw value, but the service always gets the same one.
deterministic secrets
Linked service credential propagation
After a Docker-image service starts, RailDock inspects the running container to discover generated passwords. Apps that reference those passwords via ${{ linked.service.VAR }} have their env vars updated and their containers restarted automatically.
container-inspect sync
Webhook-triggered deploys
Every service gets a unique token-authenticated webhook URL. Push a payload from GitHub or GitLab and RailDock validates the HMAC signature (X-Hub-Signature-256 for GitHub, X-Gitlab-Token for GitLab), finds matching services with auto-deploy enabled, and queues a deploy idempotently.
HMAC-verified
Canvas project view
Services appear as draggable cards on an infinite pan/zoom canvas. Connection lines show which apps are linked to which databases. Card positions persist to the database. Click a card to open the full service panel with all tabs: deploy, logs, terminal, variables, domains, storage, database, data, metrics, backups.
persistent positions
Topology-aware template deploys
When deploying a multi-service template (e.g. Chatwoot with Sidekiq, Postgres, and Redis), RailDock runs a topological sort on the depends_on graph and deploys services in dependency order, cancelling dependents if an upstream deploy fails.
DAG-ordered deploys
Automatic domains & SSL
Configure a base domain on your server (e.g. apps.example.com) and every new service gets a subdomain automatically. Magic DNS services (sslip.io, nip.io, traefik.me) embed the server's public IP in the hostname so no DNS config is needed. Custom domains with Let's Encrypt one-click enabled.
magic DNS support
Automatic scheduled backups
Create daily, weekly, or monthly backup schedules per database or storage volume. A background worker runs them automatically every minute, enforces retention, and marks backups complete only after their artifact is persisted and SHA-256 verified.
run every minute
Off-site encrypted destinations
Ship backups to S3-compatible or Cloudflare R2 buckets. Artifacts are encrypted with AES-256-GCM before multipart upload using a per-destination recovery key that is shown exactly once. PostgreSQL PITR streams WAL every minute.
AES-256-GCM
Read-only data browser
Browse tables and rows straight from the UI for Postgres, MySQL, and MariaDB services. SQL is generated and validated server-side — you never write raw queries — and credential drift is detected with a clear "out of sync" banner.
tables & rows
Recovery drills & PITR
Every Sunday, RailDock restores the latest database and volume backups into isolated, disposable resources and verifies their checksums — then always cleans up. PostgreSQL point-in-time recovery keeps daily base backups plus continuous WAL archives.
verified restores
Manifest system

Declare your stack. Preview the diff. Apply by severity.

Write a TOML file that describes your entire project — services, env vars, storage, scaling, proxy config. RailDock diffs it against the live server state and tells you what will happen before anything changes.

raildock.toml

What is RailDock?

RailDock is a self-hosted PaaS. You install it on a Linux server and it becomes a full platform: deploy apps from git or Docker images, provision and link databases, manage domains and SSL, stream live logs, open interactive terminals into containers, run scheduled backups and recovery, and define your entire infrastructure as a TOML manifest.

What it is — from reading the code

RailDock is a Rails 8 API with a React 19 frontend, shipped as a single Docker image. It manages every phase of a deploy — provisioning, builds, networks, environment variables, domains, scaling, backups — over SSH. It maintains its own PostgreSQL database for service records, deployment history, environment variables, and encrypted credentials (SSH keys, Git tokens — stored with Lockbox AES-256-GCM).

The React frontend communicates with a Rails API. Real-time features (log tailing, deployment progress, interactive terminal, server provisioning) use ActionCable WebSockets. Background work (builds, template deploys, manifest applies, scheduled backups, malware scans, metrics sampling) runs through Solid Queue.

Deploys are executed by a hardened SSH-driven deployment engine. You interact with RailDock, not the engine.

What it is not

  • It is not a managed hosting service. You run it on your own server and you own the infrastructure.
  • It is not a multi-server orchestrator. Each project maps to one server. You can register and provision multiple servers and have different projects on each, but there is no cross-server coordination.
  • It is not a thin wrapper around a CLI. RailDock has its own service model, networking layer, manifest system, reconciliation pipeline, and backup/recovery subsystem.

What works today

  • Full deploy loop — git repos and Docker images, with real-time log streaming during build
  • Interactive terminal — PTY session into any running container via xterm.js
  • 307 one-click templates — full multi-service stacks deployed with topology-aware sequencing
  • Manifest reconciler — TOML-declared infrastructure with diff preview and severity-classified apply
  • Service linking — connection injection with DATABASE_URL and credential propagation
  • Webhook deploys — per-service token URLs with HMAC verification for GitHub and GitLab
  • Domains, SSL, and auto-provisioned subdomains
  • Organizations and RBAC — teams, deploy keys, GitHub App integration per org
  • Database ops — provision, link, backup, restore, read-only data browser for Postgres, MySQL, MariaDB, Redis
  • Backups & recovery — automatic scheduled backups, PITR for Postgres, volume snapshots, encrypted S3/R2 destinations, weekly recovery drills
  • Server provisioning — bootstrap script for new remote hosts, or fully automated provisioning
  • External reverse proxy mode — for servers with an existing Traefik instance
  • Operations — real metrics with 30-day history, malware scanning, SSL status checks, in-app updates

Known limitations

  • No password reset UI — reset passwords from the Rails console: User.find_by(email: "...").update!(password: "newpass")
  • Single server per project — no multi-server orchestration
  • No preview environments
  • Read-only data browser — browse tables and rows, but not run arbitrary queries or write

Installation

RailDock ships as a single Docker image. The install script handles key generation, secret bootstrapping, and initial server connection in one pass.

Requirements

  • Linux server (Ubuntu 22.04+ recommended)
  • Docker — installed automatically by the installer if missing
  • Port 8888 open — RailDock listens here so ports 80/443 stay for your proxy
  • curl

Quick install

curl -sSL https://raw.githubusercontent.com/mona-chen/raildock/main/install.sh | bash

The installer does the following, in order:

  1. Checks for Docker and installs it if missing (via get.docker.com)
  2. Checks for the deployment runtime and installs it if missing (INSTALL_DOKKU=1 is the default)
  3. Installs the Postgres, Redis, MySQL, and Mongo datastore plugins
  4. Installs the Nixpacks and Railpack builders and starts a managed BuildKit container
  5. Raises sshd connection limits (MaxStartups)
  6. Clones the repo into the install directory (default /opt/raildock)
  7. Generates an Ed25519 SSH key pair in data/dokku-ssh/ and registers it with the runtime
  8. Auto-detects an existing Coolify/Traefik proxy container and switches to external proxy mode
  9. Writes .env with generated secrets (JWT, Lockbox, AR-encryption keys, DB URLs)
  10. Creates a fresh backend/config/credentials.yml.enc inside the pulled image
  11. Pulls ghcr.io/mona-chen/raildock/raildock:latest and starts the stack
  12. Waits for the API to respond, then creates the "Local Server" record automatically

Variants

# Reuse an existing reverse proxy (auto-detection also works) PROXY_MODE=external EXTERNAL_PROXY_NETWORK=proxy curl -sSL .../install.sh | bash # Managing only remote servers — skip local runtime install INSTALL_DOKKU=0 curl -sSL .../install.sh | bash # Bypass the runtime presence check entirely SKIP_DOKKU_CHECK=1 curl -sSL .../install.sh | bash # Build the image from source instead of pulling BUILD_FROM_SOURCE=1 ./install.sh

External proxy mode also supports EXTERNAL_PROXY_HTTP_ENTRYPOINT (default web), EXTERNAL_PROXY_HTTPS_ENTRYPOINT (default websecure), EXTERNAL_PROXY_CERT_RESOLVER, and EXTERNAL_PROXY_REDIRECT_MIDDLEWARE. In external mode the runtime's managed proxy is stopped and the global proxy is set to none; RailDock applies process-scoped Docker labels directly through the runtime's docker-options plugin. The external Traefik itself is never started, stopped, or reconfigured by RailDock.

Upgrading

cd /opt/raildock RAILDOCK_VERSION=latest ./install.sh
After every install or upgrade, back up .env and backend/config/master.key. These are the encryption keys for all SSH keys and Git tokens stored by RailDock. They cannot be recovered if lost.

Team invitations & SMTP

Team invitations require outgoing SMTP. Set SMTP_ADDRESS, SMTP_PORT, SMTP_USERNAME, SMTP_PASSWORD, and MAIL_FROM in .env, or configure SMTP in Settings after install. Until SMTP is configured, invitations are still created but the UI warns that the invite link must be shared manually.

Uninstall

./uninstall.sh

This stops and removes the RailDock containers, volumes, and data. Use --keep-data to preserve backups and keys. It does not touch apps you deployed through RailDock.

Architecture

RailDock is a Rails 8 API backend with a React 19 frontend, deployed as a single Docker image managed by supervisord. All communication with servers happens over SSH.

Process layout inside the container

supervisord ├── nginx — serves the React frontend; reverse-proxies /api to Puma ├── puma — Rails API (ActionCable included) └── solid-queue — background job workers (deploys, templates, manifests, backups, scans)

Data flow

Browser (React 19 / Vite) │ REST + WebSocket (ActionCable) ▼ Puma (Rails 8.1) ←→ PostgreSQL (RailDock's own DB) │ SSH (Net::SSH) ▼ Deployment engine on host server │ ▼ Running app containers + datastore plugin instances

Key backend services

  • DokkuEngine — SSH runner for the deployment engine. Wraps every command category: apps, config, domains, storage, proxy, ports, Traefik, datastore operations, cron, resource limits, metrics, and an interactive PTY class. Maintains a persistent SSH session per deploy job to avoid connection storms during one-click template installs.
  • HostEngine — Runs raw Docker commands on the host (network management, container inspection, volume snapshots, docker pull, container existence checks) that are not available through the engine's SSH interface. Uses the same SSH session pooling.
  • ManifestParser — Parses raildock.toml, raildock.json, app.json, railway.toml, and railway.json into a normalized ManifestDesiredState. Handles format auto-detection. Replaces ${{ ... }} template variables with internal markers resolved at apply time.
  • ManifestReconciler — Diffs the desired state against the current DB + server state, producing typed Change objects in 6 ordered apply phases with 3 severity tiers.
  • ChangeClassifier — Maps manifest fields to one of three severities: reload, restart, or redeploy.
  • ProjectNetworkManager — Creates and manages a per-project Docker bridge network so services can reach each other by internal hostname. Configures the engine's attach-post-create hook to attach containers to the network before they start, preventing DNS race conditions.
  • TemporaryDomainService — Auto-provisions a public domain for new services. If the server's base domain is a magic DNS service (sslip.io, nip.io, traefik.me), embeds the server's public IP in the hostname. Otherwise generates a subdomain and optionally enables Let's Encrypt.
  • ExternalProxyConfigurator — For servers in "external" proxy mode, disables the engine's built-in proxy and applies Traefik Docker labels to route traffic from an external Traefik instance.
  • TraefikLabelBuilder — Generates the full set of Traefik router and service labels for HTTP+HTTPS routing, TLS cert resolvers, and wildcard certificates.
  • PortDetector — Multi-step port discovery: manifest port → domain target port → container /proc/net/tcp listeners → Docker EXPOSE → engine ports:report → 80/5000 default.
  • ComposeToManifest — Best-effort converter from Docker Compose YAML to raildock.toml. Maps image names to service categories and converts port/volume/env/depends_on declarations, warning on unsupported features.
  • BackupArtifactStore — SHA-256 checksums, AES-256-GCM encryption, local + remote persistence, and verified materialization of backup artifacts.
  • DatabaseViewer — Read-only table/row inspection for Postgres, MySQL, and MariaDB via validated, quoted SQL piped through the datastore's connect command.
  • MalwareScanner — Container filesystem scans for webshells, drop dirs, and index backdoors. Report-only, surfaced as warning activity events.

ActionCable channels

  • LogsChannel — Tails service logs over a dedicated SSH connection, parses timestamp/process/level, strips ANSI codes, broadcasts over WebSocket. Each subscription gets its own thread with a stop token for clean shutdown.
  • DeploymentsChannel — Broadcasts deployment status events with log chunk streaming during the build phase.
  • TerminalChannel — Opens a PTY session for interactive shells. Forwards keystrokes (base64-encoded) and resize events. Restricted to project owners and org admins/owners.
  • ServerSetupChannel — Streams remote server provisioning logs to the setup wizard.
  • ProjectChannel — Invalidates project queries and surfaces manifest-apply failures.

Servers & provisioning

A server is a host that RailDock manages over SSH. You register servers by providing a hostname and SSH private key. RailDock validates the connection, detects versions, and stores the key encrypted with Lockbox.

Auto-configured local server

When RailDock starts for the first time with no servers registered, it reads the SSH key from /data/dokku-ssh/id_ed25519 (generated by the install script) and automatically creates a "Local" server record pointing at the same host. This gives you a working deployment environment with zero configuration.

Adding a server

From the Servers page, click "Add Server". The setup wizard has two steps:

  1. Prepare server — choose proxy mode (managed or external), copy the organization's public key, and run a one-line curl | bash bootstrap command on the remote host as root.
  2. Connect — enter name, host/IP, admin user, deployment user, proxy mode, base domain, and auto-domains toggle, then validate.

Validating streams live provisioning logs over WebSocket while the host is set up.

What the bootstrap script does

The script (returned by GET /api/organizations/:id/server_bootstrap, run as root) does all of the following:

  1. Adds the organization's public key to /root/.ssh/authorized_keys
  2. Raises sshd connection limits (MaxStartups 100:30:200)
  3. Installs Docker via get.docker.com if missing
  4. Frees port 80 (stops conflicting services unless running in external proxy mode)
  5. Installs the deployment runtime
  6. Configures the proxy (external mode sets the global proxy to none)
  7. Installs the Postgres, Redis, MySQL, and Mongo datastore plugins
  8. Installs Nixpacks and Railpack builders and starts the BuildKit container
  9. Adds the same public key to the deployment user's authorized_keys

For fully automated provisioning, add the organization public key to an admin user's ~/.ssh/authorized_keys first so ProvisionServerJob can connect and run the bootstrap for you — no manual step required.

Proxy modes

  • managed (default) — the runtime's own Traefik proxy handles routing on ports 80/443.
  • external — an existing Traefik instance handles routing. Provide the Docker network your Traefik container is attached to; RailDock applies process-scoped labels directly via the runtime's docker-options plugin and never touches your Traefik.

When you validate a server connection, RailDock detects the active proxy type (traefik, nginx, caddy, haproxy, openresty). This is stored as the server's default proxy and inherited by new services.

Base domains & auto-domains

If you set a base domain on a server (e.g. apps.example.com), RailDock auto-provisions a subdomain for every new service (e.g. myproject-api.apps.example.com). Magic DNS services are detected by name — sslip.io, nip.io, and traefik.me embed the server's public IP in the hostname so no DNS configuration is needed.

Importing running Docker containers

On a server, click "Import containers" to scan running Docker containers (docker ps + inspect) and import any of them as RailDock services — preserving image, environment, published ports, and bind mounts. Each imported app gets a deployment queued automatically.

Projects & networks

A project groups related services — typically one application with its databases, caches, and workers. Every project lives on one server and gets its own isolated Docker network.

Project network

When a project is created, RailDock generates a private Docker bridge network named rd-{slug}-{id}. Every service in the project is connected to this network so services can reach each other by internal hostname without going through the public internet or the proxy.

RailDock configures the runtime's docker-options:add deploy with --network rd-{slug}-{id} so the container is attached before it starts, preventing the DNS race conditions that occur when you connect a container to a network after it boots.

Internal hostnames

Each service is assigned an internal hostname based on its name (e.g. a service named redis is reachable at redis from other services in the same project). RailDock injects these as env vars (e.g. REDIS_HOST=redis) when a link is established.

Environments

Projects have an environment field: production, staging, or development. This is a label — it does not change runtime behavior, but it appears on service cards on the canvas and in the project list.

Shared variables

Projects support shared variables — key-value pairs accessible to all services in the project via ${{ shared.VAR }} in manifests. Useful for values like app name, region, or shared API endpoints.

Project-wide actions

From the canvas toolbar you can deploy all apps, restart all services, stop all services, or cancel all pending deployments at once. Deploys run in dependency order via a topologically-sorted sequence.

Services

A service is anything deployed in a project: an app, a database, a cache, or any Docker image. All services share the same data model — their type and subtype determine how RailDock manages them.

Managed-by

Every service has a managed_by field:

  • ui (default) — config is owned by the UI. Changes apply immediately.
  • manifest — config is owned by the raildock.toml manifest. UI edits are stored as overrides and overwritten on the next manifest apply.
  • hybrid — manifest provides the baseline; UI edits overlay it on apply.

Service naming

Every service gets an app name generated as {project-name}-{service-name} (parameterized). For example, a service named api in a project named My App becomes my-app-api. Database services follow the same convention.

Deploy sequence

Every deploy runs through a deterministic multi-phase pipeline. Understanding it explains why deploys take the time they do, and why certain failure modes occur.

The full sequence

  1. Re-sync manifest (push triggers) — For manifest-managed services, a push-triggered deploy also re-syncs the manifest from the repo.
  2. Wait for linked databases — If the service has linked datastores, RailDock polls them (up to 120 seconds) until they respond on their info command or their TCP port is open.
  3. Connect linked datastores to the project network — Ensures network aliases exist before the app boots.
  4. Ensure app exists — Creates the app if it doesn't exist yet. Idempotent.
  5. Sync environment variables atomically — Replaces the full env set in one operation.
  6. Sync domains — Applies all configured hostnames.
  7. Sync storage mounts — Applies each configured volume.
  8. Apply proxy settings — Managed proxy, external Traefik labels, or proxy disabled.
  9. Apply docker options — Per-phase (build/deploy/run) options.
  10. Apply resource limits — CPU/memory/GPU constraints per process type.
  11. Set git deploy branch and builder — Also sets the expected container port mapping before the build.
  12. Build and deploy — For Docker images: pre-pulls, then deploys with real-time log streaming (one retry on transient extraction failures). For git repos: syncs, then rebuilds with streaming logs.
  13. Detect port — Reads the running container's listening port.
  14. Re-apply port mappings — Maps the detected container port.
  15. Scale processes — Applies each process type's configured quantity.
  16. Connect to project network and sync credentials — Connects the container, ensures aliases, injects internal hostnames. For Docker-image services, inspects the running container to discover generated passwords and propagates them to linked apps.
  17. Prune and verify — Prunes exited containers and re-checks SSL certificate status for all domains.
The entire sequence uses a single persistent SSH session to avoid connection storms. On one-click template deploys with multiple services, each service deploy runs serially inside the same session, and a separate sequence job cancels any deployment whose dependency failed.

Stale deployments (pending > 30 min, building/deploying > 2 hours) are automatically failed by the reconciler job.

Builders control how RailDock turns your source code into a running container. The builder you choose determines which build backend is used.

Webhook triggers

Every service has a unique token-authenticated webhook URL. Posting to it triggers a deploy. You can also register a shared webhook that matches services by repository name.

Per-service webhook URL

Visible in the service panel under Deploy. Format:

{RAILDOCK_API_URL}/api/services/{id}/webhooks/{token}/deploy

No signature verification — the token in the URL is the secret. POST any body to trigger a deploy. Optionally pass a branch parameter.

Generic webhook (repo-matching)

POST {RAILDOCK_API_URL}/api/webhooks/deploy

Matches services by git repository. Supports:

  • GitHub — verifies X-Hub-Signature-256 HMAC with WEBHOOK_SECRET env var
  • GitLab — verifies X-Gitlab-Token against WEBHOOK_SECRET
  • Generic — verifies X-Webhook-Secret header or token query param

Only deploys services that have auto_deploy: true and whose configured branch matches the pushed ref. Idempotent — uses the GitHub delivery ID or a commit SHA hash as the idempotency key to prevent duplicate deploys from re-delivered webhooks.

Rollback

You can roll back any git-deployed service to a previous commit by selecting a past deployment in the Deploy tab.

Rollback creates a new Deployment record with the previous deployment's branch and commit SHA, then runs the standard deploy sequence using that commit. The full deploy pipeline runs — env vars, domains, storage, build — so rollback is a clean re-deploy, not a container swap.

Rollback requires the deployment to have a recorded commit SHA. Deployments triggered without a specific commit (e.g. a branch-only deploy with no commit in the payload) cannot be rolled back precisely and will return an error.

For Docker image services, rollback pins the image tag from the previous deployment's log output. This requires the image tag to still be available in the registry.

Git sources & GitHub App

Git sources connect RailDock to your code hosting accounts so you can browse repos, branches, and directories when configuring or deploying services.

Token-based sources

Connect GitHub, GitLab, Bitbucket, or Gitea with a personal access token. Each source is scoped to either a personal account or an organization. For personal sources, only the account owner can access repos; for org sources, all org members can browse repos when configuring a service. Tokens are stored encrypted (Lockbox AES-256-GCM).

GitHub App

Connecting a GitHub App enables automatic push-triggered deploys and seamless repository access without managing OAuth tokens or webhook secrets per repo. The admin panel provides a "GitHub App Manifest" flow that creates a GitHub App with the correct permissions automatically.

How the GitHub App works

  1. After a user installs the app, GitHub redirects to RailDock's callback URL
  2. RailDock verifies the installation, creates or updates a GitSource, and queues a repo sync
  3. Push events hit /api/github-apps/webhook with event verification
  4. On push, RailDock finds matching services by repo and queues deploys

When deploying a git-backed service, RailDock exchanges the installation ID for a short-lived installation token from the GitHub API. The token is embedded in the clone URL for the duration of the deploy only. No long-lived tokens are stored for git fetch operations.

Deploy keys

Generate Ed25519 deploy keys per organization to authenticate with private git repositories. Keys are generated server-side, stored encrypted, and the private key is only exposed once at creation time. Use the public key to grant read access on your git host.

Manifests — introduction

A RailDock manifest is a TOML or JSON file that declares your entire project: services, env vars, databases, storage, links, scaling, proxy, and deploy behavior. It is the closest thing to infrastructure-as-code in RailDock.

Supported formats

  • raildock.toml — primary format, full feature set, auto-detected
  • raildock.json — JSON equivalent, same schema
  • app.json — Heroku-native format, limited to its feature set
  • railway.toml / railway.json — Railway-style manifests with [build]/[deploy] blocks

Format is auto-detected from content structure when no filename hint is given. You can also import an existing Docker Compose file — RailDock converts it to raildock.toml and warns on unsupported features.

Basic example

# raildock.toml [[services]] name = "api" builder = "nixpacks" source = { type = "git" } [services.scaling] web = 1 [services.env] RAILS_ENV = "production" SECRET_KEY_BASE = "${{ secret() }}" [[services.storage]] host = "api-uploads" container = "/app/storage" [services.checks] enabled = true wait = 5 timeout = 30 [[services]] name = "db" category = "database" subtype = "postgres" source = { type = "docker" } [[links]] from = "api" to = "db"

How manifests interact with live state

The manifest editor in the UI (under the Manifest tab of any project) lets you write or paste a manifest, save it, preview the diff, and apply it. Saving a manifest does not apply changes — it only stores the content and runs an auto-preview. Changes are applied only when you click "Apply".

The manifest API endpoint (GET /api/projects/:id/manifest) generates a manifest from the current live state if none is stored, so you can inspect what a manifest for your project would look like before writing one.

Template variables

Environment values in manifests and templates support ${{ ... }} variable syntax. These are resolved by RailDock at apply time, not passed literally to the runtime.

Available variables

VariableResolves toNotes
${{ secret() }}A random 32-byte hex stringGenerated once on first deploy, stable on subsequent deploys. Stored in the service's env var record.
${{ randomInt() }}A random integerRailway-compatible; generated once and stable afterwards.
${{ RAILDOCK_PUBLIC_DOMAIN }}The service's first non-localhost public domainResolved at deploy time. Requires a domain to be configured or auto-provisioned first.
${{ shared.VAR }}A project-level shared variableSet shared vars in the project settings.
${{ linked.SERVICE.VAR }}An env var value from a linked serviceResolved at deploy time. If the linked service is a docker-image service, its container is inspected first to discover generated passwords.
${{ env.VAR }}A value from the service's own environmentResolved from the current env var set.

Legacy Coolify placeholders such as $SERVICE_PASSWORD_* and $SERVICE_URL_* are also converted automatically.

How ${{ linked.* }} works

This is the most powerful and least obvious mechanism. When service A has:

REDIS_PASSWORD = "${{ linked.redis.REDIS_PASSWORD }}"

And service A is linked to a service named "redis", RailDock stores an internal marker [LINKED:redis:REDIS_PASSWORD] in the env var value. At deploy time, it:

  1. Inspects the redis container's running environment
  2. Finds the REDIS_PASSWORD that was generated by the Redis image on first start
  3. Resolves the marker to the actual password value
  4. Pushes the resolved value to service A's config
  5. Restarts service A's container so it picks up the new value

This means you don't need to know the password ahead of time — RailDock reads it from the running container after the database starts.

Reconciler & diff

The manifest reconciler diffs your declared desired state against the current live state of the project and classifies every change by its required action.

Diff process

When you save a manifest or click "Preview", the reconciler:

  1. Parses the manifest into a desired state
  2. Reads the current state from the database (services, env vars, storage mounts, domains, scaling, config)
  3. Computes the set difference: services to create, services to remove, fields to update
  4. Wraps each delta in a Change object with service_name, field, change_type (added/removed/modified), old_value, and new_value
  5. Classifies each Change using the ChangeClassifier

Change severity classification

SeverityMeaningFields that trigger it
reloadApplied with no process disruptionenv, domains, storage, proxy, traefik_labels, letsencrypt, maintenance_mode
restartService process restart, no rebuildlimits, reservations, checks, cron, scaling, restart_policy, restart_max_retries, auto_deploy, depends_on
redeployFull rebuild and redeploybuilder, docker_image, git_repo, branch, root_directory, start_command, docker_options, version, subtype, category, exposed, port

The aggregate severity of an apply is the highest severity among all changes. A single redeploy-class field change means the entire apply is classified as redeploy, even if 20 other changes are reload-only.

Apply phases

An apply runs in six ordered phases:

  1. Create — new services created in depends_on order
  2. Reload — hot-applied config (env, domains, storage, proxy, labels, letsencrypt, maintenance)
  3. Restart — scaling, checks, cron, limits, reservations, restart policy, auto-deploy
  4. Redeploy — builder, image, repo, branch, start command, port
  5. Links — service-to-service links applied
  6. Destroy — services removed from the manifest are orphaned (see warning below)
Services removed from the manifest are flagged as "orphaned" but are not automatically destroyed. You must manually destroy orphaned services from the UI to avoid data loss.

Services tagged managed_by: ui are never modified by a manifest apply, even if they appear in the manifest. Only services already tagged managed_by: manifest or newly created by the apply are touched.

Logs & terminal

Logs stream in real time over a WebSocket. The interactive terminal gives you a full PTY session into any running container.

Log streaming

The logs channel opens a dedicated SSH connection (separate from the deploy session) and tails the appropriate log command for the service type. Each log line is parsed for timestamp, process type, and message. ANSI escape codes are stripped. The frontend detects log level from message content (FATAL, ERROR, WARN, INFO, DEBUG, TRACE keywords) and colorizes accordingly.

Log features in the UI

  • Filter by log level (show errors only, hide debug, etc.)
  • Full-text search across displayed log lines
  • JSON payload pretty-printing
  • Pause/resume the live stream
  • Download the current log buffer as a text file
  • Copy individual lines to clipboard, multi-line selection
  • Expand to fullscreen

Interactive terminal

The Console tab opens a PTY via the engine's enter command (or the datastore equivalent). The frontend uses xterm.js with:

  • Shell selection: /bin/sh, /bin/bash, /bin/zsh, /bin/ash
  • Resize events forwarded to the PTY (cols × rows)
  • Output base64-encoded through the WebSocket JSON protocol
  • Ctrl+F opens an in-terminal search
  • Expand to fullscreen
  • Retry and reconnect on connection loss

One-off commands

You can also run a single command in the service's container via the run endpoint and see its output inline — useful for quick diagnostics without opening a full terminal.

Terminal access is restricted to project owners and org admins/owners. Regular org members cannot open a terminal into any service.

Service linking

Linking an app service to a database service injects a connection URL into the app's environment and wires the two services onto the project's private network.

What happens when you link

  1. A link record is created in the database
  2. RailDock calls the appropriate datastore plugin link command (postgres:link, redis:link, etc.)
  3. The runtime injects env vars like DATABASE_URL, REDIS_URL into the app
  4. RailDock reads the injected vars back and stores them in the service record
  5. For Postgres: also sets PGSSLMODE=disable on the app (internal connections don't use SSL)
  6. Both services are connected to the project's Docker bridge network with network aliases
  7. Internal hostnames are injected as env vars so apps can reach databases by name

What happens when you unlink

  1. The link record is destroyed
  2. The corresponding plugin unlink command is called
  3. Env vars injected by the link are removed from the service record

Canvas linking

On the canvas, click the link icon on any service card to open a dropdown of services you can link to or unlink from. The direction of the link determines which service gets the injected env vars — linking app → database gives the app the DATABASE_URL.

Credential propagation

For Docker-image services, after the container starts RailDock inspects its environment for generated password variables (POSTGRES_PASSWORD, MYSQL_ROOT_PASSWORD, REDIS_PASSWORD, etc.), stores them in the service record, and propagates them to linked apps that reference them via ${{ linked.service.VAR }}.

Databases

RailDock provisions and manages database services. Supported: PostgreSQL, MySQL, MariaDB, MongoDB, Redis.

Provisioning

When you create a database service, RailDock calls the corresponding datastore plugin create command immediately — not as a background job. The plugin starts the database container and configures it. The service status is set to "running" immediately after creation succeeds.

Database info

The "Database" tab in the service panel calls the plugin's info command to show the connection DSN, status, version, and other metadata, plus a generated quick-connect CLI command per subtype (psql, redis-cli, mysql, mongosh).

Backup and restore

Manual backup calls the plugin's export command and records the result in the service's backup history. Restore uploads data and calls the plugin's import command. Scheduled backups run automatically — see the Backups & schedules page.

Password discovery

For Docker-image databases (services deployed from a Docker image rather than a datastore plugin), RailDock inspects the running container after each deploy to discover generated passwords. It scans the container's environment for known password variable names and stores them in the service record. This allows linked apps to reference these passwords via ${{ linked.service.VAR }}.

Data browser

Postgres, MySQL, and MariaDB services expose a read-only data browser in the UI — see the Data browser page.

Data browser

A read-only data browser lets you inspect the contents of Postgres, MySQL, and MariaDB databases directly from the UI — no SSH, no separate client.

What you can do

  • List tables — the left sidebar shows all tables in the database
  • Browse rows — click a table to page through its rows (50 per page) in a grid
  • Inspect values — NULLs, booleans, JSON, and long strings are formatted for readability with truncation and hover tooltips

How it stays safe

The data browser never executes user-written SQL. RailDock generates the queries itself — table and column names are validated against the schema and quoted — and pipes them through the datastore's connect command. Queries are read-only, and row limits are enforced server-side.

Credential drift handling

If the stored connection details no longer match the running database (credentials were rotated outside RailDock), the browser shows a clear "credentials out of sync" banner with instructions to resync the datastore's users on the host or reconnect with updated credentials.

The data browser is strictly read-only. It supports Postgres, MySQL, and MariaDB. Redis and MongoDB do not expose a table browser.

Domains & SSL

Add custom domains from the service panel, enable Let's Encrypt with one click, or let RailDock provision a temporary public URL automatically.

Custom domains

Adding a domain applies it to the service and, for external proxy mode, refreshes the Traefik labels. DNS must already point to your server. Hostnames are normalized (protocol/port/path stripped) and wildcard hostnames are supported (via DNS challenge).

Let's Encrypt

Enabling Let's Encrypt requests a certificate for the service's domains. The engine handles certificate issuance and the ACME challenge response. Auto-renewal is managed by the engine's built-in cron job — RailDock does not need to do anything extra.

SSL status

Each domain row shows its SSL state — active / pending / failed / HTTP — and RailDock periodically probes certificates (openssl s_client on 443), auto-detects Cloudflare, and surfaces wildcard/DNS-challenge diagnostics.

Temporary domains

When a server has a base domain configured, RailDock auto-provisions a temporary domain for every new app service:

  • If the base domain is a magic DNS service (sslip.io, nip.io, traefik.me), the hostname embeds the server's public IP: {app-name}.{public-ip}.sslip.io. No DNS configuration needed — these domains resolve automatically. SSL is not enabled for magic DNS domains.
  • If the base domain is a regular domain, the hostname is {app-name}.{base-domain}. SSL is enabled via Let's Encrypt automatically.

Temporary domains are marked with a temporary: true flag and appear separately from manually-added custom domains. You can also trigger domain generation manually from the Domains tab.

Storage mounts

Persistent storage is managed as mount records that RailDock tracks in its database and applies during each deploy.

Storage mounts are defined with a host path (a named Docker volume or an absolute path on the host) and a container path (the mount point inside the container).

# In raildock.toml [[services.storage]] host = "my-app-uploads" # named Docker volume container = "/app/storage" [[services.storage]] host = "/var/data/config" # host path bind mount container = "/app/config"

Mounts are applied during the deploy sequence. Adding new mounts via the UI applies on the next deploy; they are not hot-applied to running containers.

Kinds

KindMeaning
volumeNamed Docker volume, created automatically if missing

tmpfsIn-memory filesystem

Volume file browser

Click "browse" on any mount to open a read-only file browser: navigate directories, see file sizes, and jump back up. Backed by the storage browse endpoint.

Snapshots

Click "snapshot" on any mount to take an encrypted volume snapshot (optionally shipping it to a backup destination). Snapshots can be downloaded, restored (destructively, with confirmation), or deleted — see Backups & schedules.

Backups & schedules

Database backups and volume snapshots run automatically, persist locally, and can be mirrored to encrypted off-site destinations. Nothing is marked complete until its artifact is persisted and SHA-256 verified.

Backup kinds

KindWhat it captures
databaseFull export of a datastore (Postgres, MySQL, MariaDB, MongoDB, Redis)
volumeTar.gz snapshot of a storage mount
pitr_basePostgreSQL physical base backup (daily, via pg_basebackup)
walArchived PostgreSQL WAL segments (every minute)

Manual backups

From the Backups tab: click "Create backup" for a database or "Snapshot now" for a volume. The artifact is exported, checksummed, persisted locally (and to any selected destination), and listed in the backup history with size, SHA-256, and encrypted status.

Scheduled backups

Create daily, weekly, or monthly schedules per service, with a retention count (keep-last-N, 1–30). A background job scans for due schedules every minute and executes them automatically. Volume schedules are scoped to a specific storage mount. Retention is enforced automatically after each run.

Restoring

  • From a stored artifact — download or restore directly from the backup list. Restores require confirmation.
  • From an upload — upload a .sql, .dump, or .gz file to import (max 10 GB by default).

Downloads materialize the artifact from local storage or from an encrypted destination, decrypt it, and verify its checksum before streaming.

Where artifacts live

Local artifacts are stored under RAILDOCK_BACKUPS_DIR (default storage/backups, mounted at /rails/storage/backups in production). Keep this directory on durable storage and include it in host-level disaster recovery.

Backup destinations

Send backup artifacts to off-site storage for real disaster recovery. RailDock supports S3-compatible and Cloudflare R2 destinations.

Providers

ProviderNotes
s3Any S3-compatible endpoint (AWS, MinIO, DigitalOcean Spaces, Backblaze B2, etc.)
r2Cloudflare R2

Creating a destination

In Settings → Backup Destinations, add a destination with name, provider, region, endpoint, bucket, path prefix, access key, and secret. Saving verifies the connection with a put/head/delete health probe.

Encryption & the recovery key

Every destination gets a random 64-hex-character recovery key, generated for you. Artifacts are encrypted with AES-256-GCM (1 MB streaming chunks, a 12-byte IV, and a 16-byte auth tag) before multipart upload, using the format RAILDOCK-BACKUP-V1. The recovery key is shown exactly once at creation — save it off-host. You cannot restore from that destination without it.

Save the one-time recovery key outside of RailDock. If you lose it, backups in that destination are permanently unrecoverable.

Verification & maintenance

Destinations show a verified/failed/pending status and can be re-verified at any time. Deleting a destination removes future uploads but does not delete objects already stored in the bucket.

PostgreSQL PITR

Point-in-time recovery lets you restore a Postgres database to any moment within your retention window — not just the last full backup.

How it works

  • Daily physical base backups via pg_basebackup (streaming, compressed, encrypted)
  • Continuous WAL archiving — a job runs every minute, uploading new WAL segments from the archive directory to the destination and deleting the local copies
  • Retention window — 1–90 days (default 7); base backups and WAL older than the window are pruned automatically

Enabling

In the service panel's PITR tab, pick a verified off-site destination and enable. RailDock sets wal_level=replica, archive_mode=on, an archive_timeout of 60s, and an archive command that copies %f into the container's archive directory, then restarts the datastore.

Monitoring

The PITR tab shows retention days, last base backup time, last WAL archived time, and configuration status. Errors are surfaced with a clear message.

Disabling

Disabling turns archive mode off and resets the archive command. Existing base backups and WAL are retained until the retention window passes.

Recovery drills

Recovery drills prove your backups actually restore. Every week RailDock restores the latest database and volume backups into isolated, disposable resources, verifies them, and cleans up.

What happens

Every Sunday at 3am, for each service and each backup kind (database, volume, pitr_base), RailDock takes the newest completed backup and restores it into an isolated resource:

  • Database backups — restored into a disposable, isolated datastore, verified with a readiness check, then destroyed
  • Volume backups — restored into an isolated named volume and tar-verified, then removed
  • PITR base backups — validated as a readable tar archive

A drill is skipped if one ran for that service/kind in the last 7 days. Successful drills record checksum_verified: true; the isolated resource is always removed afterward.

Running a drill manually

From the Backups tab, click the flask icon on any backup row to run an on-demand drill for that artifact.

App templates

Templates are TOML manifests that define a complete multi-service stack. Selecting one from the gallery creates all services, generates secrets, mounts storage, and deploys everything in dependency order.

Template deploy sequence

  1. Create service records — all services in the template are created in the database synchronously, so the canvas populates immediately
  2. Create pending deployment records — app services get a pending Deployment record so the UI shows "deploying" right away
  3. Create service links — from the template's [[links]] blocks
  4. Background job starts — creates apps and datastores, calls plugin link commands, syncs storage mounts
  5. Resolve runtime variables — ${{ secret() }}, ${{ RAILDOCK_PUBLIC_DOMAIN }}, and ${{ linked.* }} markers are resolved against the now-running datastores
  6. Topological deploy — the sequence job runs the full deploy for each app service in dependency order

Built-in templates

RailDock ships with 307 templates in backend/config/templates/. Categories include AI/ML tools, databases, CMS platforms, dev tools, monitoring, media servers, communication tools, productivity apps, finance, security/password managers, home automation, and more.

Remote template repositories

Set RAILDOCK_TEMPLATES_REPO to a git URL to load additional templates from a remote repository. RailDock clones/pulls the repo on startup and merges templates (remote takes precedence on ID conflicts). This supports private template libraries and community-contributed stacks.

Writing a template

# backend/config/templates/my-app.toml name = "My App" description = "A short description shown in the gallery" category = "stack" logo = "svgs/myapp.svg" [[services]] name = "app" category = "app" subtype = "docker" docker_image = "myorg/myapp:latest" source = { type = "docker" } [services.env] SECRET = "${{ secret() }}" SITE_URL = "https://${{ RAILDOCK_PUBLIC_DOMAIN }}" DB_PASS = "${{ linked.db.POSTGRES_PASSWORD }}" [[services.storage]] host = "app-data" container = "/data" [[services]] name = "db" category = "database" subtype = "postgres" source = { type = "docker" } [[links]] from = "app" to = "db"
Template values like SMTP_ADDRESS = "SMTP_ADDRESS_VALUE" are placeholder strings that users must replace before deploying. RailDock does not validate these — they will be passed as-is to the app.

Plugins & integrations

What's in the registry

Updates

RailDock can check for new versions and update itself in place.

Checking for updates

The Updates tab shows your current version and can check GitHub releases for a newer one. A background job also checks every 6 hours. Release notes link to the GitHub release.

Applying updates

Click "Apply Update" to pull the new image and restart the stack in place. When the container has no access to the host (common in managed installs), RailDock falls back to instructions for running RAILDOCK_VERSION=latest ./install.sh manually.

Auto-update

Toggle Auto-Update to apply new releases automatically when they're detected (checked every 6 hours). This is admin-only.

Security

A summary of the security controls built into RailDock. This is not an exhaustive security audit.

  • JWT authentication — tokens expire after 30 days; generated with HS256 and a random secret set at install time
  • Rate limiting — auth endpoints protected by Rack::Attack
  • Encrypted credentials — SSH keys and git tokens stored with Lockbox AES-256-GCM; the master key is in master.key (never committed to git)
  • CORS — production restricts API access to the configured frontend origin
  • CSP headers — production enforces Content Security Policy via SecurityHeaders initializer
  • FORCE_SSL — set in .env when RailDock is behind a TLS-terminating proxy
  • Webhook HMAC — generic webhooks verify X-Hub-Signature-256 (GitHub) or X-Gitlab-Token; missing authentication with a configured secret is rejected
  • Terminal authorization — the terminal channel rejects connections from regular org members; only project owners and org admins/owners can open a terminal
  • Backup encryption — off-site artifacts are AES-256-GCM encrypted with per-destination recovery keys
  • Log redaction — URLs-with-credentials, tokens, and key=value secrets are redacted from logs
  • Malware scanning — container filesystem scans for webshells and backdoors, surfaced as warnings
  • Brakeman + bundler-audit + npm audit — run in CI on every push
  • Parameter filtering — SSH keys, master key, and JWT secrets filtered from Rails logs
There is no password reset UI. To reset a password: User.find_by(email: "user@example.com").update!(password: "new-password") in the Rails console (docker exec -it raildock-backend rails console).

Local development

The full stack — Rails API, React frontend, PostgreSQL, and Solid Queue — runs locally via Docker Compose with live reload.

Requirements

  • Docker (with Docker Compose v2)

Setup

git clone https://github.com/mona-chen/raildock.git cd raildock make setup-dev # copies .env files, builds the base image, starts the stack, seeds the DB make start # full stack with live reload

The frontend is at http://localhost:5173; the API is at http://localhost:3001. Both hot-reload as you edit code.

Common make targets

make stop # stop all containers make logs # tail all service logs make logs-backend # Rails logs only make logs-frontend # Vite logs only make db # open psql console make console # open Rails console make test # frontend Vitest (in the frontend container) make test-backend # backend RSpec (in the backend container) make reset-db # drop/create/migrate the dev DB

Running tests

# Frontend (Vitest) cd app && npm test # Backend (RSpec) cd backend && bundle exec rspec

Known limitations

Things that exist in the codebase but do not work as you might expect, documented honestly.

  • No password reset UI — Use the Rails console: docker exec -it raildock-backend rails console then User.find_by(email: "...").update!(password: "...").
  • Single server per project — All services in a project run on one server. There is no multi-server orchestration.
  • No preview environments — Branch-based preview deployments are not implemented.
  • Read-only data browser — Browse tables and rows, but not run arbitrary queries or write. Redis and MongoDB have no table browser.
  • Template placeholder values — Many templates contain values like SMTP_ADDRESS_VALUE that are placeholders for user-specific configuration. These are not flagged by RailDock at deploy time and will be passed as-is to the running container.
  • Volume snapshots restore destructively — Restoring a volume snapshot overwrites the current volume contents. Confirmation is required but the original state is not preserved.
  • Scheduled jobs run in production only — Backup schedules, PITR, drills, malware scans, and metrics sampling are wired via recurring.yml under the production environment, so they don't run in local dev/test.
  • Container-level port mapping in external proxy mode — When using an external Traefik, the engine's built-in proxy and port mappings are disabled. Traffic must flow through the external proxy; services cannot be reached on their host ports directly.
  • Landing page and pricing page are unreachable in the app — HomePage.tsx and PricingPage.tsx exist in the codebase but are not in the React Router route tree. The app redirects directly to /dashboard.
