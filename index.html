How it works

Four concepts. Everything else follows.

RailDock organizes your infrastructure into a hierarchy that maps to how you actually think about deployments.

🖥
Servers
Add any Dokku host by SSH key and hostname. RailDock validates the connection, detects the Dokku version and active proxy type, and stores your SSH key encrypted at rest (AES-256-GCM). The install script auto-wires the local server so you can deploy in under five minutes.
📁
Projects
A project is a logical grouping of services that belong together — typically one application plus its databases and workers. Every project gets a private Docker bridge network (named rd-{slug}-{id}) so services can reach each other by internal hostname without going through the public internet.
⬡
Services
A service is anything you deploy: a web app, a background worker, a Postgres database, Redis, MySQL, MongoDB, or any Docker image. Apps can be built from a git repository (Nixpacks, Dockerfile, Herokuish, Railpack, Cloud Native Buildpacks, or Lambda) or deployed directly from a Docker image tag.
🔗
Links
Linking an app to a database calls Dokku's plugin link command, which injects DATABASE_URL into the app's environment and connects both services on the project network. RailDock reads Dokku's injected connection strings and mirrors them into the service record so you can see them in the UI.

Capabilities

Built for what running software actually requires

Not a feature checklist. These are the things RailDock does that save you from writing shell scripts at 2am.

Real-time log streaming
Logs stream over an ActionCable WebSocket using a dedicated SSH connection. The frontend strips ANSI codes, detects log levels (fatal/error/warn/info/debug/trace) from message content, and pretty-prints JSON payloads. For databases, the correct plugin log command is used automatically.
tailing over SSH
Interactive terminal
A full PTY session into any running container via xterm.js. Forwards keystrokes and resize events directly to the SSH channel. Supports shell selection (sh, bash, zsh, ash) and is restricted to project owners and org admins — not all users.
PTY over WebSocket
Secret injection with stable IDs
Use ${{ secret() }} in your manifest or template. RailDock generates a random value on first deploy and keeps it stable on subsequent deploys — you never see the raw value, but the service always gets the same one.
deterministic secrets
Linked service credential propagation
After a Docker-image service starts, RailDock inspects the running container to discover generated passwords. Apps that reference those passwords via ${{ linked.service.VAR }} have their env vars updated and their containers restarted automatically.
container-inspect sync
Webhook-triggered deploys
Every service gets a unique token-authenticated webhook URL. Push a payload from GitHub or GitLab and RailDock validates the HMAC signature (X-Hub-Signature-256 for GitHub, X-Gitlab-Token for GitLab), finds matching services with auto-deploy enabled, and queues a deploy idempotently.
HMAC-verified
Canvas project view
Services appear as draggable cards on an infinite pan/zoom canvas. Connection lines show which apps are linked to which databases. Card positions persist to the database. Click a card to open the full service panel with all tabs: deploy, logs, terminal, variables, domains, storage, database, metrics, backups.
persistent positions
Topology-aware template deploys
When deploying a multi-service template (e.g. Chatwoot with Sidekiq, Postgres, and Redis), RailDock runs a topological sort on the depends_on graph and deploys services in dependency order, cancelling dependents if an upstream deploy fails.
DAG-ordered deploys
Automatic domains & SSL
Configure a base domain on your server (e.g. apps.example.com) and every new service gets a subdomain automatically. Magic DNS services (sslip.io, nip.io) embed the server's public IP in the hostname so no DNS config is needed. Custom domains with Let's Encrypt one-click enabled.
magic DNS support

What is RailDock?

RailDock is a self-hosted deployment platform. You install it on a Linux server alongside Dokku, and it becomes a full PaaS control plane: deploy apps from git or Docker images, provision and link databases, manage domains and SSL, stream live logs, open interactive terminals into containers, and define your entire infrastructure as a TOML manifest.

What it is — from reading the code

RailDock operates by talking to Dokku over SSH. Every action in the UI translates to real Dokku commands executed on your server. It maintains a PostgreSQL database of its own for service records, deployment history, environment variables (stored in plaintext, as Dokku would see them), and encrypted credentials (SSH keys, Git tokens — stored with Lockbox AES-256-GCM).

The React frontend communicates with a Rails API. Real-time features (log tailing, deployment progress, interactive terminal) use ActionCable WebSockets. Background work (builds, template deploys, manifest applies) runs through Solid Queue.

What it is not

  • It is not a Dokku dashboard or admin panel. RailDock has its own service model, networking layer, manifest system, and deployment pipeline — Dokku is the execution engine it speaks to.
  • It is not a multi-server orchestrator. Each project maps to one Dokku server. You can register multiple servers and have different projects on each, but there is no cross-server coordination.
  • It is not a managed hosting service. You run it on your own server and you own the infrastructure.

What works today

  • Full deploy loop — git repos (sync + rebuild) and Docker images, with real-time log streaming during build
  • Interactive terminal — PTY session into any running container via xterm.js
  • 306 one-click templates — full multi-service stacks deployed with topology-aware sequencing
  • Manifest reconciler — TOML-declared infrastructure with diff preview and severity-classified apply
  • Service linking — Dokku plugin links with DATABASE_URL injection and credential propagation
  • Webhook deploys — per-service token URLs with HMAC verification for GitHub and GitLab
  • Domains, SSL, and auto-provisioned subdomains
  • Organizations and RBAC — teams, deploy keys, GitHub App integration per org
  • Database ops — provision, link, backup, restore for Postgres, MySQL, MariaDB, MongoDB, Redis
  • External Traefik proxy mode — for servers with an existing reverse proxy

Known limitations

  • Backup schedules run on paper only — the UI lets you create backup schedules, but there is no recurring job that executes them. Manual backups work.
  • No password reset UI — reset passwords from the Rails console: User.find_by(email: "...").update!(password: "newpass")
  • Single server per project — no multi-server orchestration
  • No preview environments
  • Metrics fallback — if Dokku's ps:report output format changes, metrics fall back to nil with a warning log

Installation

RailDock ships as a single Docker image. The install script handles key generation, secret bootstrapping, and initial server connection in one pass.

Requirements

  • Linux server (Ubuntu 22.04+ recommended)
  • Docker 20+ and Docker Compose
  • Dokku 0.38+ (installer can set it up for you)
  • Port 8888 open — RailDock listens here so Dokku's proxy keeps ports 80/443

Quick install

curl -sSL https://raw.githubusercontent.com/mona-chen/raildock/main/install.sh | bash

The installer does the following, in order:

  1. Checks for Docker; prints install instructions if missing
  2. Checks for Dokku; installs it if INSTALL_DOKKU=1 is set
  3. Generates an Ed25519 SSH key pair and writes it to data/dokku-ssh/
  4. Registers the public key with Dokku via dokku ssh-keys:add
  5. Copies .env.example to .env and fills in random secrets (JWT_SECRET_KEY, LOCKBOX_MASTER_KEY, etc.)
  6. Generates a fresh backend/config/credentials.yml.enc and master.key
  7. Pulls ghcr.io/mona-chen/raildock:latest and starts the stack
  8. Waits for the API to respond, then creates the "Local Dokku" server record automatically

Variants

# Also install Dokku INSTALL_DOKKU=1 curl -sSL .../install.sh | bash # Connecting to a remote Dokku server — skip local Dokku check SKIP_DOKKU_CHECK=1 curl -sSL .../install.sh | bash # Build the image from source instead of pulling BUILD_FROM_SOURCE=1 ./install.sh

Upgrading

cd /opt/raildock RAILDOCK_VERSION=latest ./install.sh
After every install or upgrade, back up .env and backend/config/master.key. These are the encryption keys for all SSH keys and Git tokens stored by RailDock. They cannot be recovered if lost.

Uninstall

./uninstall.sh

This stops and removes the RailDock containers and volumes. It does not touch Dokku or any apps you deployed through RailDock.

Architecture

RailDock is a Rails 8 API backend with a React 19 frontend, deployed as a single Docker image managed by supervisord. All communication with Dokku happens over SSH.

Process layout inside the container

supervisord ├── nginx — serves the React frontend; reverse-proxies /api to Puma ├── puma — Rails API (ActionCable included) └── solid-queue — background job workers (deploys, template installs, manifest applies)

Data flow

Browser (React 19 / Vite) │ REST + WebSocket (ActionCable) ▼ Puma (Rails 8.1) ←→ PostgreSQL (RailDock's own DB) │ SSH (Net::SSH) ▼ Dokku on host server │ ▼ Running app containers + Dokku plugin datastores

Key backend services

  • DokkuEngine — SSH wrapper with 60+ methods. Wraps every Dokku command category: apps, config, domains, storage, proxy, ports, Traefik, Postgres/MySQL/Redis/MongoDB/MariaDB operations, cron, resource limits, metrics, ps:report, and an interactive PTY class. Maintains a persistent SSH session per deploy job to avoid connection storms during one-click template installs.
  • HostEngine — Runs raw Docker commands on the host (network management, container inspection, docker pull, container existence checks) that are not available through Dokku's SSH interface. Uses the same SSH session pooling.
  • ManifestParser — Parses raildock.toml, raildock.json, or app.json into a normalized ManifestDesiredState. Handles format auto-detection. Replaces ${{ ... }} template variables with internal markers ([SECRET:id], [RAILDOCK_PUBLIC_DOMAIN], etc.) during parse, resolved at apply time.
  • ManifestReconciler — Diffs ManifestDesiredState against current DB + Dokku state. Produces a list of typed Change objects, each classified by ChangeClassifier.
  • ChangeClassifier — Maps manifest fields to one of three severities: reload, restart, or redeploy.
  • ServiceSettingsSync — Pushes hot-reloadable config changes (proxy settings, Traefik labels, port mappings, cron, resource limits, Let's Encrypt, maintenance mode) to Dokku immediately when a service is updated in the DB, without requiring a redeploy.
  • ProjectNetworkManager — Creates and manages a per-project Docker bridge network so services can reach each other by internal hostname. Configures Dokku's attach-post-create hook to attach containers to the network before they start, preventing DNS race conditions.
  • TemporaryDomainService — Auto-provisions a public domain for new services. If the server's base domain is a magic DNS service (sslip.io, nip.io, traefik.me), embeds the server's public IP in the hostname. Otherwise generates a subdomain and optionally enables Let's Encrypt.
  • ExternalProxyConfigurator — For servers in "external" proxy mode, disables Dokku's built-in proxy and applies Traefik Docker labels to route traffic from an external Traefik instance.
  • PortDetector — Four-step port discovery: (1) Dokku ports:report, (2) plugin-specific info commands, (3) known defaults by subtype, (4) heuristic fallback based on deploy method.
  • TraefikLabelBuilder — Generates the full set of Traefik router and service labels for HTTP+HTTPS routing, TLS cert resolvers, and wildcard certificates.
  • ComposeToManifest — Best-effort converter from Docker Compose YAML to raildock.toml. Maps image names to service categories, converts port/volume/env/depends_on declarations, and warns on unsupported features.
  • GithubAppService — Manages GitHub App installation tokens, verifies webhook signatures, and syncs accessible repositories via the GitHub API.

ActionCable channels

  • LogsChannel — Opens a dedicated SSH connection and tails the appropriate Dokku log command for the service type. Parses timestamp, process name, and log level from each line. Strips ANSI escape codes. Broadcasts to the frontend over WebSocket. Each subscription gets its own thread with a Concurrent::Atom stop token for clean shutdown.
  • DeploymentsChannel — Broadcasts deployment status events (pending → building → deploying → succeeded/failed) with log chunk streaming during the build phase.
  • TerminalChannel — Opens a PTY session via DokkuEngine's interactive_shell method. Forwards keystrokes (base64-encoded through JSON) and resize events. Restricted to project owners and org admins/owners.

Background jobs

  • DeploymentJob — Runs the full 15-step deploy sequence for one service. Concurrency-locked per service (one deploy at a time). Uses a persistent SSH session for the entire job.
  • DeploymentSequenceJob — Runs a topologically-sorted list of deployments in order, cancelling any deployment whose dependency failed.
  • TemplateDeployJob — Handles the Dokku-side setup of a one-click template deploy: creates apps and datastores, creates links, connects project networks, resolves runtime variables, then enqueues DeploymentSequenceJob.
  • ManifestApplyJob — Runs ManifestReconciler.apply! in the background and broadcasts progress over ActionCable.
  • ReconcileStaleDeploymentsJob — Runs every 10 minutes in production. Marks deployments that have been "building" for too long as failed.
  • GithubSyncReposJob — Fetches the list of accessible repositories from GitHub after a GitHub App install.

Servers

A server is a Dokku host that RailDock manages over SSH. You register servers by providing a hostname and SSH private key. RailDock validates the connection, detects Dokku and Docker versions, and stores the key encrypted with Lockbox.

Auto-configured local server

When RailDock starts for the first time with no servers registered, it reads the SSH key from /data/dokku-ssh/id_ed25519 (generated by the install script) and automatically creates a "Local Dokku" server record pointing at the Dokku instance on the same host. This gives you a working deployment envir with zero configuration.

SSH user

RailDock connects to Dokku servers as the dokku user by default. This is the standard Dokku SSH user — Dokku intercepts SSH commands and routes them through its plugin system. You can override the SSH user per server in the server settings.

Proxy detection

When you validate a server connection, RailDock runs proxy:report --global to detect the active proxy type (traefik, nginx, caddy, haproxy, openresty). This is stored as the server's default proxy and inherited by new services created on that server.

Base domain and auto-domains

If you set a base domain on a server (e.g. apps.example.com), RailDock auto-provisions a subdomain for every new service (e.g. myproject-api.apps.example.com). Magic DNS services are detected by name — sslip.io, nip.io, and traefik.me will embed the server's public IP in the hostname so no DNS configuration is needed.

External proxy mode

If your server already has a Traefik instance managing routing, set the proxy mode to "external" and provide the Docker network name your Traefik container is attached to. RailDock will disable Dokku's built-in proxy for services on that server and instely Traefik Docker labels, connecting each service's container to the proxy network.

Projects & networks

A project groups related services — typically one application with its databases, caches, and workers. Every project lives on one server and gets its own isolated Docker network.

Project network

When a project is created, RailDock generates a private Docker bridge network named rd-{slug}-{id}. Every service in the project is connected to this network so services can reach each other by internal hostname without going through the public internet or Dokku's proxy.

RailDock configures Dokku's docker-options:add deploy with --network rd-{slug}-{id} so the container is attached before it starts, preventing the DNS race conditions that occur when you connect a container to a network after it boots.

Internal hostnames

Each service is assigned an internal hostname based on its name (e.g. a service named redis is reachable at redis from other services in the same project). RailDock injects these as env vars (e.g. REDIS_HOST=redis) when a link is established.

Environments

Projects have an environment field: production, staging, or development. This is a label — it does not change runtime behavior, but it appears on service cards on the canvas and in the project list.

Shared variables

Projects support shared variables — key-value pairs accessible to all services in the project via ${{ shared.VAR }} in manifests. Useful for values like app name, region, or shared API endpoints.

Services

A service is anything deployed in a project: an app, a database, a cache, or any Docker image. All services share the same data model — their type and subtype determine what Dokku commands RailDock uses to manage them.

Managed-by

Every service has a managed_by field:

  • ui (default) — config is owned by the UI. Changes apply immediately.
  • manifest — config is owned by the raildock.toml manifest. UI edits are stored as overrides and overwritten onext manifest apply.
  • hybrid — manifest provides baseline; UI edits overlay it on apply.

Every service gets a Dokku app name generated as {project-name}-{service-name} (parameterized). For example, a service named api in a project named My App becomes my-app-api in Dokku. Database services follow the same convention.

Deploy sequence

Every deploy runs through a deterministic 15-step sequence. Understanding it explains why deploys take the time they do, and why certain failure modes occur.

The full sequence

  1. Wait for linked databases — If the service has linked datastores, RailDock polls them (up to 120 seconds) until they respond on their plugin info command or their TCP port is open. Prevents apps from booting before Postgres/MySQL/Redis is ready.
  2. Create Dokku app — Runs dokku apps:create {name} if the app doesn't exist yet. Idempotent.
  3. Configure project network — Calls ProjectNetworkManager to create the project's Docker bridge network if needed and configure Dokku's attach-post-create docker option so the container joins the network before starting.
  4. Sync environment variables — Iterates all service env vars and calls dokku config:set for each.
  5. Sync domains — Calls dokku domains:set with all configured hostnames.
  6. Sync storage mounts — Calls dokku storage:mount for each configured volume.
  7. Configure proxy — Either applies ExternalProxyConfigurator (for external Traefik mode), disables the proxy, or calls dokku proxy:set and applies nginx settings. Calls dokku proxy:enable.
  8. Apply Docker options — Calls dokku docker-options:add for each configured option (phase: build/deploy/run).
  9. Apply resource limits — Calls dokku resource:limit for each process type with CPU/memory/GPU constraints.
  10. Set git deploy branch — Calls dokku git:set deploy-branch {branch}.
  11. Build and deploy — For Docker image services: pre-pulls the image on the host, then calls git:from-image with real-time log streaming. For git repos: calls git:sync, then streams ps:rebuild. Retries once on transient overlayfs extraction failures.
  12. Detect port — PortDetector reads the running container's port via ports:report, plugin info commands, or known defaults.
  13. Sync port mappings — Calls dokku ports:set for HTTP and HTTPS, mapping host ports 80/443 to the detected container port.
  14. Scale processes — Calls dokku ps:scale for each process type's configured quantity.
  15. Connect to project network and sync credentials — Connects the container to the project network, ensures network aliases for all linked services, injects internal hostnames as env vars. For Docker image services, inspects the running container to discover generated passwords and propagates them to linked apps.
The entire sequence uses a single persistent SSH session to avoid connection storms. On one-click template deploys with multiple services, each service deploy runs serially inside the same session.

Webhook triggers

Every service has a unique token-authenticated webhook URL. Posting to it triggers a deploy. You can also register a shared webhook that matches services by repository name.

Per-service webhook URL

Visible in the service panel under Deploy. Format:

{RAILDOCK_API_URL}/api/services/{id}/webhooks/{token}/deploy

No signature verification — the token in the URL is the secret. POST any body to trigger a deploy. Optionally pass a branch parameter.

Generic webhook (repo-matching)

POST {RAILDOCK_API_URL}/api/webhooks/deploy

Matches services by git repository. Supports:

  • GitHub — verifies X-Hub-Signature-256 HMAC with WEBHOOK_SECRET env var
  • GitLab — verifies X-Gitlab-Token against WEBHOOK_SECRET
  • Generic — verifies X-Webhook-Secret header or token query param

Only deploys services that have auto_deploy: true and whose configured branch matches the pushed ref. Idempotent — uses the GitHub delivery ID or a commit SHA hash as the idempotency key to prevent duplicate deploys from re-delivered webhooks.

GitHub App

Connect a GitHub App per organization to enable automatic repo syncing and push-triggered deploys without managing webhook secrets. See GitHub App integration.

Rollback

You can roll back any git-deployed service to a previous commit by selecting a past deployment in the Deploy tab.

Rollback creates a new Deployment record with the previous deployment's branch and commit SHA, then runs the standard deploy sequence using that commit. The full deploy pipeline runs — env vars, domains, storage, build — so rollback is a clean re-deploy, not a container swap.

Rollback requires the deployment to have a recorded commit SHA. Deployments triggered without a specific commit (e.g. a branch-only deploy with no commit in the payload) cannot be rolled back precisely and will return an error.

For Docker image services, rollback pins the image tag from the previous deployment's log output. This requires the image tag to still be available in the registry.

Manifests — introduction

A RailDock manifest is a TOML file that declares your entire project: services, env vars, databases, storage, links, scaling, proxy, and deploy behavior. It is the closest thing to infrastructure-as-code in RailDock.

Supported formats

  • raildock.toml — primary format, full feature set, auto-detected
  • raildock.json — JSON equivalent, same schema
  • app.json — Heroku/Dokku native format, limited to Dokku-native features

Format is auto-detected from content structure when no filename hint is given. If a manifest is explicitly saved as app.json, it is parsed with the Heroku/Dokku schema.

Basic example

# raildock.toml [[services]] name = "api" builder = "nixpacks" source = { type = "git" } [services.scaling] web = 1 [services.env] RAILS_ENV = "production" SECRET_KEY_BASE = "${{ secret() }}" [[services.storage]] host = "api-uploads" container = "/app/storage" [services.checks] enabled = true wait = 5 timeout = 30 [[services]] name = "db" category = "database" subtype = "postgres" source = { type = "docker" } [[links]] from = "api" to = "db"

How manifests interact with live state

The manifest editor in the UI (under the Manifest tab of any project) lets you write or paste a manifest, save it, preview the diff, and apply it. Saving a manifest does not apply changes — it only stores the content and runs an auto-preview. Changes are applied only when you click "Apply".

The manifest API endpoint (GET /api/projects/:id/manifest) will generate a manifest from the current live state if none is stored, so you can inspect what a manifest for your project would look like before writing one.

Template variables

Environment values in manifests and templates support ${{ ... }} variable syntax. These are resolved by RailDock at apply time, not passed literally to Dokku.

Available variables

VariableResolves toNotes
${{ secret() }}A random 32-byte hex stringGenerated once on first deploy, stable on subsequent deploys. Stored in the service's env var record.
${{ RAILDOCK_PUBLIC_DOMAIN }}The service's first non-localhost public domainResolved at deploy time. Requires a domain to be configured or auto-provisioned first.
${{ shared.VAR }}A project-level shared variableSet shared vars in the project settings.
${{ linked.SERVICE.VAR }}An env var value from a linked serviceResolved at deploy time. If the linked service has that var, the value is propagated. If the linked service is a docker-image service, its container is inspected first to discover generated passwords.

How ${{ linked.* }} works

This is the most powerful and least obvious mechanism. When service A has:

REDIS_PASSWORD = "${{ linked.redis.REDIS_PASSWORD }}"

And service A is linked to a service named "redis", RailDock stores an internal marker [LINKED:redis:REDIS_PASSWORD] in the env var value. At deploy time (step 15), it:

  1. Inspects the redis container's running environment
  2. Finds the REDIS_PASSWORD that was generated by the Redis image on first start
  3. Resolves the marker to the actual password value
  4. Calls dokku config:set on service A with the resolved value
  5. Restarts service A's container so it picks up the new value

This means you don't need to know the password ahead of time — RailDock reads it from the running container after the database starts.

Reconciler & diff

The manifest reconciler diffs your declared desired state against the current live state of the project and classifies every change by its required action.

Diff process

When you save a manifest or click "Preview", ManifestReconciler:

  1. Parses the manifest into a ManifestDesiredState
  2. Reads the current state from the database (services, env vars, storage mounts, domains, scaling, config)
  3. Computes the set difference: services to create, services to remove, fields to update
  4. Wraps each delta in a Change object with service_name, field, change_type (added/removed/modified), old_value, and new_value
  5. Classifies each Change using ChangeClassifier

Change severity classification

SeverityMeaningFields that trigger it
reloadApplied with no process disruptionenv, domains, storage, proxy, traefik_labels, letsencrypt, maintenance_mode
restartService process restart, no rebuildlimits, reservations, checks, cron, scaling, restart_policy, restart_max_retries, auto_deploy, depends_on
redeployFull rebuild and redeploybuilder, docker_image, git_repo, branch, root_directory, start_command, docker_options, version, subtype, category, exposed, port

The aggregate severity of an apply is the highest severity among all changes. A single redeploy-class field change means the entire apply is classified as redeploy, even if 20 other changes are reload-only.

Services removed from the manifest are flagged as "orphaned" but are not automatically destroyed. You must manually destroy orphaned services from the UI or CLI to avoid data loss.

Services tagged managed_by: ui are never modified by a manifest apply, even if they appear in the manifest. Only services already tagged managed_by: manifest or newly created by the apply are touched.

Logs & terminal

Logs stream in real time over a WebSocket. The interactive terminal gives you a full PTY session into any running container.

Log streaming

LogsChannel opens a dedicated SSH connection (separate from the deploy session) and tails the appropriate log command:

Service typeCommand
App servicesdokku logs {app} -n 0 --tail
postgresdokku postgres:logs {name} --tail
redisdokku redis:logs {name} --tail
mysql / mariadbdokku mysql:logs {name} --tail
mongodokku mongo:logs {name} --tail

Each log line is parsed for timestamp, process type, and message using Dokku's standard format (2026-01-01T00:00:00Z app[web.1]: message). ANSI escape codes are stripped. The frontend detects log level from message content (FATAL, ERROR, WARN, INFO, DEBUG, TRACE keywords) and colorizes accordingly.

Log features in the UI

  • Filter by log level (show errors only, hide debug, etc.)
  • Full-text search across displayed log lines
  • JSON payload pretty-printing
  • Pause/resume the live stream
  • Download the current log buffer as a text file
  • Copy individual lines to clipboard
  • Expand to fullscreen

Interactive terminal

TerminalChannel opens a PTY via dokku enter {app} (or the database plugin equivalent for datastores like dokku postgres:enter {name}). The frontend uses xterm.js with:

  • Shell selection: /bin/sh, /bin/bash, /bin/zsh, /bin/ash
  • Resize events forwarded to the PTY (cols × rows)
  • Output base64-encoded through the WebSocket JSON protocol
  • Ctrl+F opens an in-terminal search (xterm.js search addon)
  • Expand to fullscreen
Terminal access is restricted to project owners and org admins/owners. Regular org members cannot open a terminal into any service.

Service linking

Linking an app service to a database service tells Dokku to inject a connection URL into the app's environment and wires the two services onto the project's private network.

What happens when you link

  1. A ServiceLink record is created in the database
  2. RailDock calls the appropriate Dokku plugin link command: postgres:link {db} {app}, redis:link, etc.
  3. Dokku injects env vars like DATABASE_URL, REDIS_URL, DOKKU_POSTGRES_* into the app
  4. RailDock reads Dokku's injected vars back out via config:show and stores them in the service record
  5. For Postgres: also sets PGSSLMODE=disable on the app (Dokku internal connections don't use SSL)
  6. Both services are connected to the project's Docker bridge network with appropriate network aliases
  7. Internal hostnames are injected as env vars so apps can reach databases by name

What happens when you unlink

  1. The ServiceLink record is destroyed
  2. The corresponding Dokku plugin unlink command is called
  3. Env vars injected by the link (source: "dokku-link") are removed from the service record

Canvas linking

On the canvas, click the link icon on any service card to open a dropdown of services you can link to or unlink from. The direction of the link determines which service gets Dokku's injected env vars — linking app → database gives the app the DATABASE_URL.

Databases

RailDock provisions and manages database services through Dokku plugins. Supported: PostgreSQL, MySQL, MariaDB, MongoDB, Redis.

Provisioning

When you create a database service, RailDock calls the corresponding Dokku plugin create command (postgres:create, redis:create, etc.) immediately — not as a background job. The Dokku plugin starts the database container and configures it. The service status is set to "running" immediately after creation succeeds.

Database info

The "Database" tab in the service panel calls the plugin's info command (postgres:info, etc.) to show the connection DSN, status, version, and other metadata directly from Dokku.

Backup and restore

Manual backup calls the plugin's export command and records the result in the service's backup history. Restore uploads data and calls the plugin's import command.

Backup schedules can be created in the UI, but there is currently no scheduled job that executes them. They will not run automatically. Use cron or an external scheduler to call the backup API endpoint on a schedule.

Password discovery

For Docker-image databases (services deployed from a Docker image rather than a Dokku plugin), RailDock inspects the running container after each deploy to discover generated passwords. It scans the container's environment for known password variable names (POSTGRES_PASSWORD, MYSQL_ROOT_PASSWORD, REDIS_PASSWORD, etc.) and stores them in the service record. This allows linked apps to reference these passwords via ${{ linked.service.VAR }}.

Domains & SSL

Add custom domains from the service panel, enable Let's Encrypt with one click, or let RailDock provision a temporary public URL automatically.

Custom domains

Adding a domain calls dokku domains:add {app} {hostname}. DNS must already point to your server. Removing a domain calls dokku domains:remove.

Let's Encrypt

Enabling Let's Encrypt calls dokku letsencrypt:enable {app}. Dokku handles certificate issuance and ACME challenge response. Auto-renewal is managed by Dokku's built-in cron job — RailDock does not need to do anything extra.

Temporary domains

When a server has a base domain configured, RailDock auto-provisions a temporary domain for every new app service:

  • If the base domain is a magic DNS service (sslip.io, nip.io, traefik.me), the hostname embeds the server's public IP: {app-name}.{public-ip}.sslip.io. No DNS configuration needed — these domains resolve automatically. SSL is not enabled for magic DNS domains.
  • If the base domain is a regular domain, the hostname is {app-name}.{base-domain}. SSL is enabled via Let's Encrypt automatically.

Temporary domains are marked with a temporary: true flag and appear separately from manually-added custom domains.

Generate domain button

You can also trigger domain generation manually from the Domains tab. This calls generate_domain which creates the domain record, calls dokku domains:add, and syncs the port mappings to route traffic correctly.

Storage mounts

Persistent storage is managed by Dokku's storage plugin. RailDock tracks mounts in its database and syncs them to Dokku during each deploy.

Storage mounts are defined with a host path (a named Docker volume or an absolute path on the host) and a container path (the mount point inside the container).

# In raildock.toml [[services.storage]] host = "my-app-uploads" # named Docker volume container = "/app/storage" [[services.storage]] host = "/var/data/config" # host path bind mount container = "/app/config"

Mounts are applied during step 4 of the deploy sequence using dokku storage:mount. Adding new mounts via the UI are applied on the next deploy. They are not hot-applied to running containers.

Named volumes (no leading /) are created automatically by Dokku if they do not exist. Host bind mounts must already exist on the server.

App templates

Templates are TOML manifests that define a complete multi-service stack. Selecting one from the gallery creates all services, generates secrets, mounts storage, and deploys everything in dependency order.

Template deploy sequence

  1. Create service records — All services in the template are created in the database synchronously (before the background job starts), so the canvas populates immediately
  2. Create pending deployment records — App services get a pending Deployment record so the UI shows "deploying" state right away
  3. Create service links — ServiceLink records are created from the template's [[links]] blocks
  4. TemplateDeployJob starts (background) — Creates Dokku apps and datastores, calls plugin link commands, syncs storage mounts
  5. Resolve runtime variables — ${{ secret() }}, ${{ RAILDOCK_PUBLIC_DOMAIN }}, and ${{ linked.* }} markers are resolved against the now-running datastores
  6. Topological deploy — DeploymentSequenceJob runs the full deploy for each app service in dependency order

Built-in templates

RailDock ships with 306 templates in backend/config/templates/. Categories include AI/ML tools, databases, CMS platforms, dev tools, monitoring, media servers, communication tools, productivity apps, and more.

Remote template repositories

Set RAILDOCK_TEMPLATES_REPO to a git URL to load additional templates from a remote repository. RailDock clones/pulls the repo on startup and merges templates (remote takes precedence on ID conflicts). This supports private template libraries and community-contributed stacks.

Writing a template

# backend/config/templates/my-app.toml name = "My App" description = "A short description shown in the gallery" category = "stack" logo = "svgs/myapp.svg" # optional, in public/templates/logos/ [[services]] name = "app" category = "app" subtype = "docker" docker_image = "myorg/myapp:latest" source = { type = "docker" } [services.env] SECRET = "${{ secret() }}" SITE_URL = "https://${{ RAILDOCK_PUBLIC_DOMAIN }}" DB_PASS = "${{ linked.db.POSTGRES_PASSWORD }}" [[services.storage]] host = "app-data" container = "/data" [services.checks] enabled = true wait = 10 timeout = 30 [[services]] name = "db" category = "database" subtype = "postgres" source = { type = "docker" } [[links]] from = "app" to = "db"
Template values like SMTP_ADDRESS = "SMTP_ADDRESS_VALUE" are placeholder strings that users must replace before deploying. RailDock does not validate these — they will be passed as-is to the app.

Organizations & RBAC

Organizations let multiple users collaborate on projects. Access is controlled by membership roles at the organization level.

Roles

RolePermissions
ownerFull access. Can delete the organization, manage all members, all projects, all settings.
adminCan manage projects, services, git sources, and deploy keys. Cannot delete the org or demote other admins/owners.
memberRead access to projects and services. Cannot deploy, create services, or access the terminal.

Deploy keys

Generate Ed25519 deploy keys per organization to authenticate with private git repositories. Keys are generated server-side, stored encrypted, and the private key is only exposed once at creation time. Use the public key to grant read access on your git host.

Git sources

Git sources track connections to GitHub, GitLab, Bitbucket, or Gitea. Each source is scoped to either a personal account or an organization. For personal sources, only the account owner can access repos. For org sources, all org members can browse repos when configuring a service.

GitHub App integration

Connect a GitHub App to enable automatic push-triggered deploys and seamless repository access without managing OAuth tokens or webhook secrets per repo.

Setup

Go to Settings → Integrations in RailDock. The admin panel provides a "GitHub App Manifest" flow that creates a GitHub App with the correct permissions automatically. After creation, install the app on your GitHub account or organization.

How it works

After a user installs the GitHub App, GitHub redirects to RailDock's callback URL. RailDock:

  1. Receives the installation ID and fetches installation details from the GitHub API to verify the account type
  2. Creates or updates a GitSource record tied to the installation
  3. Queues GithubSyncReposJob to fetch accessible repositories
  4. Push events from GitHub hit /api/github-apps/webhook with event verification
  5. On push, RailDock finds matching services by repo and queues deploys

Per-deploy authentication

When deploying a git-backed service, RailDock exchanges the GitHub App installation ID for a short-lived installation token from the GitHub API. The token is embedded in the clone URL (x-access-token:{token}@github.com/{repo}) for the duration of the deploy. No long-lived tokens are stored for git fetch operations.

Security

A summary of the security controls built into RailDock. This is not an exhaustive security audit.

  • JWT authentication — tokens expire after 30 days; generated with HS256 and a random secret set at install time
  • Rate limiting — auth endpoints protected by Rack::Attack
  • Encrypted credentials — SSH keys and git tokens stored with Lockbox AES-256-GCM; the master key is in master.key (never committed to git)
  • CORS — production restricts API access to the configured frontend origin
  • CSP headers — production enforces Content Security Policy via SecurityHeaders initializer
  • FORCE_SSL — set in .env when RailDock is behind a TLS-terminating proxy
  • Webhook HMAC — generic webhooks verify X-Hub-Signature-256 (GitHub) or X-Gitlab-Token; missing authentication with a configured secret is rejected
  • Terminal authorization — TerminalChannel rejects connections from regular org members; only project owners and org admins/owners can open a terminal
  • Brakeman + bundler-audit — run in CI on every push (see .github/workflows/ci.yml)
  • Parameter filtering — SSH keys, master key, and JWT secrets filtered from Rails logs
There is no password reset UI. To reset a password: User.find_by(email: "user@example.com").update!(password: "new-password") in the Rails console (docker exec -it raildock-backend rails console).

Backup & restore

RailDock's own PostgreSQL database can be backed up and restored with the included scripts. App databases are backed up separately through the service panel.

RailDock platform backup

cd /opt/raildock ./scripts/backup.sh # Creates: backups/raildock_production-YYYYMMDD-HHMMSS.sql.gz # Restore ./scripts/restore.sh backups/raildock_production-20260601-120000.sql.gz
Also back up .env and backend/config/master.key. The database backup does not include these. Without them, all encrypted SSH keys and git tokens are permanently unreadable.

Application database backup

From the service panel "Backups" tab, click "Create backup". RailDock calls the Dokku plugin export command (postgres:export, redis:export, etc.) and stores a reference to the backup. Click "Restore" and upload a backup file to call the corresponding import command.

Backup schedules exist in the UI but are not automatically executed. No recurring job runs them. Set up an external cron job to POST to the backup API endpoint if you need scheduled backups.

Local development

The full stack — Rails API, React frontend, PostgreSQL, and Solid Queue — runs locally via Docker Compose.

Requirements

  • Docker and Docker Compose
  • Ruby 3.4+ (for running backend tests locally)
  • Node.js 20+ (for running frontend tests locally)

Setup

git clone https://github.com/mona-chen/raildock.git cd raildock make setup-dev # copies .env files, runs migrations, seeds the DB make start # starts API, frontend, and workers with live reload

make stop # stop all containers make logs # tail all service logs make logs-backend # Rails logs only make db # open psql console make console # open Rails console make test # run Vitest (frontend unit tests)

Running tests

# Frontend (Vitest) cd app && npm test # Backend (RSpec) cd backend && bundle exec rspec

Known limitations

Things that exist in the codebase but do not work as you might expect, documented honestly.

  • Backup schedules are not executed — The UI allows creating a backup schedule with a frequency and retention count, and these records are stored in the database. However, recurring.yml only has two entries: ReconcileStaleDeploymentsJob (every 10 minutes) and a SolidQueue cleanup job. No job executes backup schedules. Manual backups from the service panel work correctly.
  • No password reset UI — Use the Rails console: docker exec -it raildock-backend rails console then User.find_by(email: "...").update!(password: "...").
  • Single server per project — All services in a project run on one Dokku server. There is no multi-server orchestration.
  • No preview environments — Branch-based preview deployments are not implemented.
  • Metrics parsing is brittle — The metrics endpoint parses ps:report output with a regex. If Dokku changes its output format, metrics will return nil and log a warning. There is no fallback data.
  • Landing page and pricing page are unreachable — HomePage.tsx and PricingPage.tsx exist in the codebase but are not in the React Router route tree. The app redirects directly to /dashboard.
  • Template placeholder values — Many templates contain values like SMTP_ADDRESS_VALUE that are placeholders for user-specific configuration. These are not flagged by RailDock at deploy time and will be passed as-is to the running container.
  • GitHub App account type is detected from GitHub, not from state — If a GitHub App install is re-processed (re-delivered callback), the organization association is determined fresh from GitHub's API. This is intentional to avoid trusting frontend state, but it means the GitSource organization association can change if the GitHub account type changes.
  • Container-level port mapping for external proxy mode — When using external Traefik proxy mode, Dokku's built-in proxy and port mappings are disabled. Traffic must flow through the external proxy. Services cannot be reached on their host ports directly.
