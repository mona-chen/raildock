Deleting a project is now a background operation that keeps going when you close the tab, and service connection activity is measured by default instead of waiting to be switched on.

### Highlights

- **Project deletion runs on the host's queue, not in the request.** `DELETE /api/projects/:id` answers immediately with `202` and `ProjectDeletionJob` takes the destruction snapshot, removes the Dokku apps, datastores and volumes, and records the outcome. A second request attaches to the deletion already queued or running instead of starting a second one.
- **Progress and failures are visible on the project card.** While a deletion is queued or running the card says so and keeps polling; once it finishes the project disappears. A failed attempt stays on the card with its reason — `snapshot_required` offers **Retry snapshots** or **Permanently delete without snapshot**, and any other error offers a plain retry.
- **A wedged deletion cannot lock a project forever.** Other service operations are refused with an explanation while a deletion is in flight, but after two hours without progress it is treated as stalled: the card unlocks and retrying re-queues it.
- **Destructive teardown has its own worker.** `maintenance` is separate from `deployments` and `backups`, so a long deletion can neither hold up a deploy nor delay PostgreSQL WAL archiving.
- **Data safety is unchanged.** Every datastore and persistent volume is still exported to a verified destination before anything is removed; `force_destroy_data` remains the only way past that and is logged as a warning.
- **Redis caches are provisioned as datastores.** A manifest or import that declares a `cache`/`redis` service now creates it through the Redis plugin instead of failing as an app that needs a Git repository.
- **Repository imports keep what you reviewed.** A `raildock.toml` import is regenerated from the reviewed manifest, so the branch and builder you picked in the import flow are the ones stored, instead of the raw file's values.
- **Service connection activity is measured by default.** New and existing servers sample direct TCP traffic with live-only retention (no history rows) until you turn it off; an explicitly disabled server stays off, and disabling stops host sampling entirely.

### Limits worth knowing

- Sampled TCP is not a flow ledger: connections that open and close between samples are missed, and UDP, Unix sockets, host networking and indirect proxy/NAT paths are not covered. Missing permissions or tools report unavailable telemetry, not measured zero.
- The project row survives until the job finishes, so a deletion that fails keeps its services and domains intact and retryable.
- Retrying a stalled deletion snapshots and removes whatever is left, so a project that was half-removed finishes rather than rolling back.
- Flow collection still needs root SSH, Linux 5+, Python 3, `nsenter` and a modern `ss`; nothing is installed on the host.

### Tests

- New coverage for the deletion job (snapshot failure, data-loss acknowledgement, SSH failure, duplicate delivery, stalled pickup), the `202` API contract, the project lock messaging and the card states.
- Full suites: 1548 backend examples and 174 frontend tests, plus the host-side proxy-setup and network-flow suites.
