Remote servers are easier to provision and monitor, backups work consistently across engines, and PostgreSQL can be recovered to a point in time into a new service.

### Highlights

- **Remote server setup got safer.** The server form has an explicit SSH port, applied by every SSH client (deploys, host metrics, console, logs and health checks) instead of assuming 22. A read-only preflight checks the OS, architecture, passwordless sudo, disk, RAM, ports 80/443 and whether the host can reach the bootstrap URL before anything is modified. Failures stop the setup; warnings are reported and the bootstrap continues.
- **Provisioning is bound and shell-safe.** The setup id is issued by the server and tied to the requesting user and organization, the bootstrap command shell-escapes every value, non-root admins use `sudo -n`, and a host that already runs RailDock is refused before SSH. Host keys are pinned on create and cannot be overwritten.
- **Server health is monitored.** A job every five minutes refreshes each server's status, check time and error over a short `version` probe. It holds no database lock during SSH and runs on the maintenance queue.
- **Pick the right server when creating a project.** The New Project dialog now offers a server picker and the API uses the chosen server. A server outside the organization is rejected with `422 invalid_server`; without a choice, RailDock prefers a connected server from the organization.
- **Backup schedules actually save.** Dashboard requests were silently dropping every schedule because the API expected snake_case keys. Requests now send snake_case (camelCase aliases still work), destinations survive edits, a frequency change reschedules the next run, and resuming a paused schedule schedules a full interval out.
- **Backups cover every engine.** Logical dumps are gated on a datastore's backup/restore capability, so Redis can be backed up like a database and apps are refused as database schedules. Retention is 1–90 with cadence defaults, restore drills probe readiness per engine instead of assuming Postgres, and volume snapshots follow the service's default destinations.
- **More destinations, proven before saving.** Create and edit now probe the destination before persisting anything. Presets cover Backblaze B2, Wasabi, DigitalOcean Spaces, Hetzner, MinIO and GCS alongside S3 and R2; each row shows its last verification and error, and `scripts/decrypt-backup.rb` recovers an artifact offline with its key.
- **Point-in-time recovery into a new service.** `POST /api/services/:id/recovery/pitr/restore` stages a new PostgreSQL service in the same project and environment. RailDock replays WAL into an isolated instance, dumps the source database while it is up, imports it into the new datastore, and verifies the user-table count before marking it running. The live database is never written; a failure removes only what the restore created. The PITR tab now has a “Recover to a new service” flow with window and name checks, confirmation and progress.
- **Storage and recovery live together.** The service panel keeps Networking for domains only; volumes, snapshots, database backups and PostgreSQL point-in-time recovery share the Storage/Backups area with a protection summary and reusable recovery components. Restores, deletes and force prompts use the same confirmation dialog, and the console keeps its draft when a request fails.

### Security and reliability

- Backup destination endpoints are now validated as real HTTP(S) URLs with a host, rejecting embedded credentials, queries, fragments and trailing garbage.
- The SSH port and PITR restore migrations no longer share a version, so fresh installs and upgrades apply both.
- A server that still hosts projects cannot be deleted (`422 server_has_projects`).

### Limits worth knowing

- Point-in-time recovery requires a verified destination. The target must fall after the oldest completed base backup and no later than the last archived WAL; only the service's own database is copied, not extra databases in the same cluster.
- The preflight is intentionally read-only. Busy ports 80/443 are a warning because an external proxy or an existing Dokku install may already own them; a private bootstrap URL is also only a warning.
- Server health is a five-minute probe, not a live status. A failed check records `status_error` and the next sweep retries it.
- Backups still cannot complete without a destination that accepted and served back a probe object; a restore point that only exists on this host is reported as such.

### Tests
